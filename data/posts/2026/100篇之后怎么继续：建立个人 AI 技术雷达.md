# 100篇之后怎么继续：建立个人 AI 技术雷达

写到第 100 篇的时候，最容易出现一种疲惫：每天都有新模型、新框架、新协议、新榜单，刚把一个概念讲明白，名字又换了一轮。你追得越快，收藏夹越长，真正动手的时间却越来越少。

我也经历过这个阶段。看到新项目就收藏，看到论文就下载，看到别人做出 Demo 就觉得自己也应该马上跟上。过了一阵子回头看，资料堆了很多，但脑子里只有零散的名词：知道它们出现过，却不知道它们解决什么问题，更不知道哪些已经值得放进生产系统。

后来我开始建立自己的 AI 技术雷达。它不是一个“所有热点排行榜”，而是一套帮助自己做取舍的系统：哪些东西值得理解，哪些值得实验，哪些可以观察，哪些应该明确忽略。

## 一、技术雷达不是收藏夹

我把技术分成四个区域：

```text
采用 Adopt：已经验证，正在项目中使用
实验 Trial：值得做小实验，观察投入产出
观察 Assess：有潜力，但证据和生态还不够
暂缓 Hold：暂时不投入，记录原因
```

同一个技术会随着证据变化移动位置。一个刚发布的模型可能先放在观察区，跑过真实数据后进入实验区，经过成本、安全和维护验证，才有资格进入采用区。

```ts
type RadarItem = {
  name: string
  category: 'model' | 'framework' | 'protocol' | 'hardware' | 'method'
  status: 'adopt' | 'trial' | 'assess' | 'hold'
  solves: string
  evidence: string[]
  nextExperiment?: string
  revisitAt: string
}
```

重点是 `solves` 和 `evidence`。一个技术如果说不清解决什么问题，或者只有宣传材料没有自己的验证，就不应该因为热度直接进入采用区。

## 二、先建立问题地图，再追技术名称

不要从“最近有什么新模型”开始学习，而要从自己的问题开始：

- 我的 RAG 为什么召回不准？
- Agent 为什么会重复调用工具？
- 端侧模型为什么发热和变慢？
- 结构化输出为什么偶尔解析失败？
- 推理成本为什么持续上升？

问题地图可以按层次组织：

```text
用户体验
  ├─ 质量、延迟、可解释性
应用能力
  ├─ RAG、工具、Agent、多模态
模型能力
  ├─ 训练、推理、对齐、压缩
基础设施
  ├─ GPU、服务、评测、观测
```

当新技术出现时，先问它落在哪个问题上。它如果只是多了一个名字，却没有改善你的质量、速度、成本或安全，就不必急着学习。

## 三、信息源要分层

不同信息源适合回答不同问题：

1. 官方文档：接口、限制和使用方式。
2. 原始论文：方法、实验和假设。
3. 源代码：真正实现了什么。
4. 工程案例：在真实流量和约束下表现如何。
5. 社区讨论：失败经验、边界和生态反馈。
6. 新闻和短帖：发现线索，不作为最终证据。

短帖适合告诉你“有个新东西出现了”，但不能证明它值得生产使用。看到一个惊人的 benchmark，至少回到论文或官方报告，检查数据、基线、硬件和指标。看到一个很酷的 Demo，至少在自己的小数据集上试一次。

我现在会给每条信息加一个证据等级：听说、官方声明、可运行代码、独立复现、线上数据。证据等级越低，结论越应该保守。

## 四、用小实验代替无休止的阅读

学习一个技术最好的方式，通常不是看十篇介绍，而是做一个两小时内能完成的小实验。实验要有问题、基线、指标和停止条件：

```ts
type Experiment = {
  question: string
  baseline: string
  variant: string
  metric: string
  budgetMinutes: number
  stopCondition: string
  result: string
}
```

比如不要泛泛地研究“新 Embedding 好不好”，而要问：“在我的中文 FAQ 数据上，新 Embedding 的 Recall@5 是否提升至少 3%，延迟和成本是否仍在预算内？”问题越具体，实验越容易结束。

小实验不需要追求完整复现。它的目标是判断是否值得继续投入。结果不理想也有价值，因为它帮你排除了一个方向。真正浪费时间的不是实验失败，而是没有问题、没有指标、没有终点地一直看资料。

## 五、建立自己的基准集

技术雷达如果没有固定基准，很容易被新 Demo 带走。准备一组和自己业务相关的样本：常见问题、边界问题、无答案问题、高风险问题和长尾表达。任何新模型、新 Prompt、新检索器都用同一组样本比较。

```ts
type PersonalBenchmark = {
  version: string
  cases: Array<{
    id: string
    input: string
    expected: string
    risk: 'low' | 'medium' | 'high'
  }>
}
```

自己的基准集不必很大，但要稳定、可追溯、定期更新。只看公开榜单，无法知道某个模型是否适合你的语言、领域、延迟和成本边界。

## 六、把采用决策写成记录

技术选型最怕靠记忆。每次把某个技术放进采用区，都写一份短决策记录：

```text
选择：Hybrid Search
问题：纯向量检索对产品编号召回不稳定
证据：业务基准集 Recall@5 从 0.81 提升到 0.93
代价：增加关键词索引和维护成本
边界：暂不用于跨语言检索
回滚：保留旧向量检索路径
复查日期：三个月后
```

这份记录让未来的自己知道当时为什么选择它，也防止团队把一个特定条件下有效的方案误认为永远正确。技术决策不是宣誓，而是基于当前证据的暂时结论。

## 七、定期淘汰过时知识

学习系统不仅要增加内容，还要删除和降级。模型 API 会废弃，框架接口会变化，某些优化只在旧硬件上成立，几年前的文章可能把当时的限制说成今天的事实。

每月或每季度检查：

- 代码示例还能运行吗？
- 文档中的模型和价格是否仍然有效？
- 依赖版本是否有安全问题？
- 当初的基准和现在的业务还相关吗？
- 有没有更简单的替代方案？

过时内容不一定删除，可以标记版本、日期和适用范围。知识库里明确写着“已过时”，比让读者误以为它仍然适用更诚实。

## 八、保护注意力和学习节奏

技术变化快，不代表你必须每天追所有更新。可以设置固定的情报窗口：平时只收集线索，每周筛选一次，每月做少量实验。没有进入问题地图的热点，先放在观察区，不要打断当前正在完成的工作。

```text
线索 → 筛选 → 小实验 → 记录证据 → 采用 / 观察 / 暂缓
```

学习的节奏应该和项目节奏匹配。正在处理生产故障时，优先修复可靠性；产品要降成本时，优先研究路由和缓存；准备新功能时，再投入多模态或 Agent。技术学习不是逃离现实，而是更好地解决现实问题。

## 九、100 篇文章应该留下什么

一百个标题本身没有那么重要，重要的是它们是否形成了可以复用的判断框架：

- 理解一个模型时，看能力、数据、成本和边界。
- 设计一个 Agent 时，看状态、工具、权限和恢复。
- 上线一个 RAG 时，看评测、监控、增量和回滚。
- 选择一个框架时，看抽象、源码、生态和退出成本。
- 复现一篇论文时，看环境、数据、指标和误差。

这些问题会比某个短期流行的名字活得久。写文章也是一种研究：把模糊感觉写成白话，把实验结果留下，把失败原因讲出来，未来遇到相似问题时，就不用从零开始。

## 总结：真正的成长是越来越会选择

我最后想留下的，不是“永远保持好奇”这种正确但没用的话，而是一条更具体的建议：给每一个新技术安排一个问题，给每一个问题安排一个小实验，给每一个实验安排一个停止条件。

大模型世界不会等你学完再更新，也没有一张永远正确的最终清单。我们能做的是建立自己的雷达，知道什么已经验证，什么值得试，什么只是传闻，什么暂时不必投入。把信息变成证据，把证据变成选择，把选择沉淀成可复用的系统。

写完 100 篇以后，你不需要继续追逐 1000 个名词。你应该比开始时更清楚：面对一个新模型，先问什么；面对一个新框架，怎么试；面对一个漂亮结果，怎样怀疑；面对一个失败实验，能学到什么。技术最终会变化，但这种判断力会一直跟着你。
